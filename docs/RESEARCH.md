## Once Upon A KATAMARI on PC (Steam): ids, engine, asset formats, modding tools, safety and content facts

Once Upon A KATAMARI (Steam app 1880620, RENGAME/Bandai Namco) is a Unity 6 game built with the IL2CPP backend and the URP renderer, and it ships its content as Addressables asset bundles. Two community mods on GitHub confirm the IL2CPP backend: shookietea/OUAK-IGT (MelonLoader) and ItsSeafoamy/Once-Upon-an-Archipelago (BepInEx 6 BE #783 IL2CPP). Both hard-code the install folder steamapps\common\OnceUponaKATAMARI, so the game is already moddable with standard Unity tooling. The data folder is OnceUponaKATAMARI_Data. Movies are CRI Sofdec2 .usm files in OnceUponaKATAMARI_Data\StreamingAssets\Movie, and the build includes the CriWare runtime, so CRI ADX2 (.acb/.awb/HCA) is the likely music format, but no source shows those files on disk. The game code lives in namespace App.KatamariSin. Rollable objects are listed in CollectionAssetTable.Instance.MonoCategoryTable(), a list of MonoInfo entries whose Param records carry an id and a SyncMonoID. In-game they are 'Mono' objects whose behaviour class is MainGameMonoBase. The Archipelago world has an auto-generated table of 3,757 object IDs (about 3,744 unique English names such as Tomato, Daruma Head, Relaxing Spartan Soldier, Deer Haniwa and Three-headed Shiba) with the stages each appears in. PCGamingWiki, via search snippets, lists Steam DRM, Criware for audio and cutscenes, PlayFab for multiplayer and Direct3D 11. I found no evidence of Denuvo or anti-cheat. The online part is the 4-player KatamariBall mode. Assets look readable without decryption: The Models Resource has PC rips (dae/fbx/png) of Pokkle, Signolo, Harvest and Young King, and TCRF extracted .usm movies. I could not verify bundle encryption, the type-tree presence, the exact Unity 6000.x version or the music container format, because steamdb, pcgamingwiki, tcrf, steamcommunity, gamebanana and the Steam store are all blocked from this sandbox. For a mashup, the host-side mod should find the install through libraryfolders.vdf -> appmanifest_1880620.acf -> installdir, read the Addressables bundles with a Unity serialized-file reader, and rebuild the meshes and textures with the host's own materials rather than loading Katamari prefabs. It should decode music with vgmstream or VGAudio. Katamari itself never needs to run.

**Risks**
- Primary sources were blocked from this sandbox (steamdb.info, store.steampowered.com, pcgamingwiki, tcrf, steamcommunity, gamebanana, mobygames, katamaripedia). Several facts come from WebSearch summaries, not pages I read, and should be checked on a real install.
- The exact Unity 6000.x version, Addressables version (catalog.json vs catalog.bin), type-tree presence in bundles and any custom bundle header or encryption are all unknown. If type trees are stripped, reading MonoInfo/CollectionAssetTable needs Cpp2IL-generated type info from GameAssembly.dll plus global-metadata.dat.
- Loading Katamari's bundles directly with AssetBundle.LoadFromFile inside a different Unity host is likely to fail or render wrong. Bundles are tied to Unity version and platform, materials use URP and Toony Colors Pro shaders the host lacks, and prefabs reference IL2CPP MonoBehaviours (MainGameMonoBase etc.) that do not exist in the host. Extracting raw Mesh and Texture2D and building host-native materials is safer.
- Music may be HCA inside CRI .acb/.awb. If it is HCA-encrypted and no public key exists (vgmstream lists none for Katamari), decoding would mean pulling a key out of the game binary. That is a gray area, so stop and decide with the user. If the music is a Unity AudioClip (FSB5), a different decoder is needed.
- Addressables bundle file names are hashed and change between patches (1.1.0, 1.1.1, ...), so hard-coded bundle names will break. Locate bundles through the catalog or by name prefix.
- Music differs per player: Side A and Side B DLC tracks exist only if owned, so the mashup must fall back to base-game tracks.
- Memory: decompressing whole bundles can use many GB of RAM (toolkit note: 865 MB bundle to 8.7 GB). Stream or lazily read .resS/.resource data.
- Never bundle extracted Katamari content or the community object tables. OUAK-IGT and Once-Upon-an-Archipelago show no license, so their code and data cannot be copied into a release. Use them only as reference and regenerate data from the user's own install at runtime.
- Katamari's online features (KatamariBall over PlayFab) must not be touched. The mashup should never launch Katamari or talk to its services; it should only read files from disk.
- Minimum OS for the game is Windows 11. Linux/Proton players have the install under a compatdata prefix, and path discovery must handle multiple Steam libraries.

**Recommendation**

Treat Once Upon A KATAMARI as a read-only data source at runtime; never launch it. 1) Locate it. Read the Steam path (HKCU\Software\Valve\Steam\SteamPath, or the default), parse steamapps/libraryfolders.vdf, and look in each library for steamapps/appmanifest_1880620.acf. Take installdir (expected 'OnceUponaKATAMARI') and confirm OnceUponaKATAMARI_Data and GameAssembly.dll exist. If it is missing, show an in-game message such as 'Once Upon A KATAMARI (Steam 1880620) not found; install it to load its objects and music' and keep running without Katamari content. 2) Find the content. Open the Addressables catalog under OnceUponaKATAMARI_Data/StreamingAssets/aa (location still to be confirmed) and find bundles by catalog key or name prefix, because hashes change per patch. 3) Read meshes and textures. If the host's mod side is .NET (a BepInEx or MelonLoader host), embed AssetsTools.NET (MIT) to open UnityFS bundles in-process. Decode Mesh vertex and index buffers with a small decoder ported from AssetStudio's MIT mesh code, and Texture2D with AssetsTools.NET's texture helpers or a BCn decoder. Then build host-native meshes with host materials (a simple toon or unlit shader, because Katamari uses URP plus Toony Colors Pro). Do not AssetBundle.LoadFromFile Katamari prefabs into another engine. If the host's mod side is not .NET (for example Java/Fabric or UE4SS Lua/C++), bundle a self-contained helper that the mod runs on first launch. It can be a .NET helper using AssetsTools.NET, or Python using UnityPy (MIT). It writes a private local cache (glTF/PNG/OGG) in the user's folder, which the mod then loads. The cache is never shipped. 4) Map objects. Read the game's own CollectionAssetTable / MonoInfo data (Param.id, SyncMonoID, names, and sizes if present) from the bundles. If type trees are stripped, generate type layouts with Cpp2IL (MIT) or Il2CppDumper (MIT) from GameAssembly.dll plus global-metadata.dat. Use the Archipelago world's 3,757-entry object table only as a cross-check, because it has no license. Pick props that suit Silent Hill 2's mood and scale them by their katamari size class. The game's own fog system is a useful reference. 5) Music and voice. If the audio is CRI ADX2 (.acb/.awb/HCA), decode it at runtime with libvgmstream or vgmstream-cli (ISC-style, redistributable) or VGAudio (MIT, C#), and stream it through the host's audio API. If the HCA is encrypted with no public key, stop and flag it rather than pulling keys from the binary. Skip the .usm movies unless they are needed. 6) Test on a real install with UnityExplorer (GPL-3.0, dev-only and not bundled) under MelonLoader or BepInEx 6 BE #783. Verify bundle paths, type trees and the audio format first, because those are the main unknowns.

## SILENT HILL 2 (2024 remake, Bloober Team / Konami), PC: install layout, containers, audio, asset paths, modding routes, licenses, and how to load its real assets at runtime

SH2 (2024) is Steam app 2124490, installed to steamapps/common/SILENT HILL 2. The Unreal project folder is SHProto, the launcher is SHProto.exe and the real exe is SHProto/Binaries/Win64/SHProto-Win64-Shipping.exe. The engine is Unreal Engine 5.1, confirmed by three independent sources: CUE4Parse files the game under its UE5.1 entries, the UE4SS game-support list tags it '501', and the Vortex extension sets ENGINE_VERSION 5.1.1.0. Content is IoStore: SHProto-Windows.pak/.utoc/.ucas plus global.utoc in SHProto/Content/Paks, with no .sig signature files. CUE4Parse (Apache-2.0) has a dedicated GAME_SilentHill2Remake entry and only one game-specific code path (instanced static mesh data), so normal UE5.1 parsing should work. Two things are still unknown and are what the plan depends on: whether the containers are AES-encrypted (no public source says either way; the mod can read the Encrypted bit at byte offset 80 of the .utoc header) and how to get a .usmap mappings file. A community .usmap was shared in Oct 2024 through a Gildor forum thread and an X thread, but it isn't on GitHub, and every UE5 asset read needs one. Audio is Wwise: Konami's announcement names it. Banks/media are unverified on disk. CUE4Parse's WwiseProvider looks in <Project>/Content/WwiseAudio and resolves AkAudioEvent to .wem. FModel turns .wem into WAV by running vgmstream-cli (ISC license). On DRM, launch coverage says there was no Denuvo, the Steam exe has a Steam DRM wrapper, and GOG sells it DRM-free since May 2025. No anti-cheat is known. Modding today uses pak mods in SHProto/Content/Paks/~mods, UE4SS 3.0.1 with an EngineVersionOverride of 5.1, LogicMods, and praydog's SH2R-UEVR. The one verified internal asset path is James's AnimBP under /Game/Game/Characters/Humans/JamesSunderland/. Every other character, monster and sound path is still unknown. CUE4Parse targets net10.0, so it should not run inside a Mono or BepInEx host. It should run as a separate self-contained converter on the player's PC that reads the paks from disk and never launches or patches SH2.

**Risks**
- AES encryption is unknown. If SHProto-Windows.utoc has the Encrypted flag (0x02 at header byte 80), every route needs a key. The only public keys sit on community lists (e.g. cs.rin.ru, which FModel's README points to), and the other way to get one is extracting it from the Steam exe, which carries a Steam DRM wrapper. Getting a key either way may count as working around a protection: decrypting the player's own copy with a key published by others is common in modding (FModel, UModel and CUE4Parse all take user-supplied keys), but the toolkit's safety rules forbid DRM tampering and key extraction from executables. If encrypted: stop, don't bundle a key, and raise it with the user. No legal conclusion is offered here.
- A .usmap mappings file is required and none is on GitHub. Shipping a community-made .usmap is legally unclear: it holds only reflection names and types, no assets, but it comes from the game. Generating one on the player's machine means launching SH2 with UE4SS (EngineVersionOverride 5.1) or Dumper-7, which breaks the one-click flow.
- Oodle: if the containers are Oodle-compressed and SH2 ships no oo2core DLL, CUE4Parse would by default download an Epic-derived Oodle build from a third-party GitHub release at runtime. That has unclear redistribution rights, is a network side effect, and may be blocked offline. Alternatives: the GPL-3.0 ooz decoder (copyleft would spread to the helper) or the MIT oozextract Rust crate (provenance as a port of GPL code is worth a look).
- CUE4Parse targets net10.0. It can't run inside a Mono or BepInEx host, so a separate self-contained helper exe is needed. That adds size (SkiaSharp and ImageSharp natives) and a first-run conversion step.
- Animations: CUE4Parse can't write glTF animations (only PSA, UEFormat and USD). The host needs a PSA/UEFormat importer, or the helper needs its own glTF animation writer built on SharpGLTF. Retargeting James's skeleton onto Katamari-style rolling poses is its own job.
- Materials don't carry over. Only textures (PNG) and parameters export, so James's skin, hair and cloth shading has to be rebuilt in the host's renderer. Hair may be cards or a groom (unknown).
- Asset paths beyond James are unverified. Monster and character folder names, the radio-static and music Wwise events, and fog settings have to be found on a real install (FModel search, or the Nexus audio-ID lookup mod) before coding.
- Audio: the Wwise version and codec (Vorbis or Opus) are unknown. Opus or other codecs pull FFmpeg (LGPL) DLLs into the vgmstream bundle, which brings LGPL notice and replaceability duties. Music is likely interactive (switch containers), so getting complete Yamaoka tracks may mean picking segments.
- Version drift: patches change asset layout (e.g. the Nov 2024 patch grew .ucas by about 5.7 MiB), and a .usmap is tied to a build. The converter should key its cache by buildid (appmanifest) and the .utoc hash, then re-convert.
- Store variants: the Steam, GOG and Epic installs share the SHProto layout. The Xbox/Game Pass install (WinGDK) may sit in a protected WindowsApps folder and was not researched.
- The brief assumed Denuvo at launch; sources contradict that. The Steam DRM wrapper remains, so the mod must never touch, patch or launch-wrap SHProto-Win64-Shipping.exe.

**Recommendation**

Treat SH2 purely as a data source read from disk. Never launch it, inject into it, or touch SHProto-Win64-Shipping.exe, which has the Steam DRM wrapper.

1. **Find the install.** Ship a small self-contained .NET helper (Apache-2.0 CUE4Parse + CUE4Parse-Conversion; credit via the NOTICE file) next to the host-game mod. On first run it:
   - parses Steam libraryfolders.vdf → appmanifest_2124490.acf → installdir 'SILENT HILL 2';
   - falls back to the GOG registry (2051029707 / 1225972913) and the Epic manifests (c4dc308a1b69492aba4d47f7feaa1083);
   - checks that SHProto/Content/Paks/SHProto-Windows.utoc exists, and if not, has the host show 'SILENT HILL 2 not found'.

2. **Gate on the .utoc header.** Before any parsing, read the header:
   - Encrypted bit set (0x02 at offset 80): stop with an in-game message and escalate to the user. Never bundle or derive a key.
   - Otherwise, log the compression method names.

3. **Mount the containers.** Use DefaultFileProvider with VersionContainer(EGame.GAME_SilentHill2Remake) and a .usmap. Settle how the .usmap is sourced (shipped, generated, or engine-only) as an explicit decision with the user.
   - For Oodle, load a DLL found in the player's own SH2 install if there is one.
   - Otherwise use a vetted open decoder (MIT oozextract compiled to a DLL and plugged into CUE4Parse's decompression hook). Disable OodleHelper's silent download.

4. **Export James and the cast.** Start from /Game/Game/Characters/Humans/JamesSunderland/ and do the same for the other characters:
   - SkeletalMesh to .glb (EMeshFormat.Gltf2), textures to PNG.
   - Animations to PSA or UEFormat, or better, have the helper write glTF animation channels itself from CUE4Parse's converted CAnimSet using SharpGLTF (MIT), so the host only needs a glTF loader.

5. **Export audio.** Use CUE4Parse's WwiseProvider (AkAudioEvent → .wem) and decode with a bundled vgmstream-cli (ISC, plus the BSD/LGPL codec DLLs and their notices) to WAV/OGG. Look up the radio-static, ambience and Yamaoka music events by name or ID on a real install first.

6. **Cache locally.** Write everything to a per-user cache keyed by Steam buildid plus the .utoc hash, so nothing from SH2 is ever redistributed. Re-convert when the build changes.

7. **Optional fog values.** Read fog and post-process parameters (ExponentialHeightFog and volumetric fog settings) from SH2 map packages to drive the host's fog. A curated, hand-tuned fallback isn't a stand-in asset.

8. **Verify on a real Windows install before building.** Check, in this order: encryption flag, compression method, .usmap availability, and James's mesh path. All four are currently unknown or unverified, and the first two can block the whole SH2 side.

## What the universal-modder toolkit says about building "James pushes the katamari" (Once Upon A KATAMARI + SILENT HILL 2 remake, both secondary, inside a third Melty-catalog host)

(a) In the toolkit's terms, this concept is not "native geometry transfer". That route means both real games are running and the guest streams its meshes live. Here neither guest runs, so the closest fit is two routes combined. The first is Asset conversion (mashup Pattern 1: a converter reads the user's own install and writes a private local cache). The second is a rebuilt guest mechanic inside a real host (Pattern 5 / transplant: Katamari's rolling rules rewritten as a headless sim, with the host as the view). The nearest worked precedents are Bloons TD 6 in Minecraft, FPV LOGIC (UE 5.3) in Minecraft, Halo 3 MCC in Minecraft and Left 4 Dead in Minecraft. All of them use a converter run at install time that writes a private cache in formats the host can load. None of them parses the guest's archives inside the host on every launch. In all of them the user runs the converter by hand. The toolkit has no recipe for running it automatically on first launch and knows nothing about Melty, so that step is new design work. The toolkit's installer rules still apply to it: stage, verify, swap, write the completion marker last, re-run after a guest update. (b) The toolkit's first slice for this mix has three steps. First, the mechanic runs on a greybox with no game data and is checked by a headless bench. Second, convert one model and load it in the host, checked by preview sheets rendered by re-reading the converter's own output. Third, a scripted host scene checked with the log plus a scaled screenshot that someone actually looks at. (c) No code that can be reused as-is reads Unity bundles or UE5 IoStore. What can be reused: um scan's Steam library discovery code (MIT), um publish check, um backup, um win, um video and um kb, plus documented format layouts and pitfalls. (d) On AES, the toolkit contradicts itself. unreal.md calls keys "public for most games" and mentions AESDumpster. The more specific knowledge-base rules say deriving keys from an executable breaks a protection measure and is not allowed. They also say keys and key-extraction methods are never published. So an encrypted SH2 archive would block the SH2 asset path within toolkit rules. (e) um win runs only on native Windows or WSL. I confirmed here that it exits with an error on this Linux container. Real-run testing has to happen on the user's Windows PC, and synthetic tests here do not count as a real run.

**Risks**
- SH2 encryption is the biggest risk. If SILENT HILL 2's .utoc/.ucas/.pak are AES-encrypted, toolkit rules leave no sanctioned way to read SH2 assets: do not derive the key from the exe (Naruto note), and do not ship or publish a key or an extraction method (publishing note). unreal.md's 'keys are public / AESDumpster' line conflicts with this, and the stricter knowledge-base rules should win. Whether SH2 is encrypted is unknown to the toolkit and must be checked on the user's install without a key (header/TOC flags).
- The knowledge base has nothing on either game (kb search katamari / silent hill return nothing), so engine version, archive format, skeletal-mesh layout and audio format must all come from fresh recon (um scan on the user's PC).
- No toolkit precedent auto-runs the converter. Every precedent (BTD6, FPV LOGIC, Halo 3, L4D) has the user run a Python command by hand. Melty's one-click rule needs a first-launch trigger, a bundled converter runtime, progress UI and resumability. BTD6-scale extraction took about 3.5 min and 1.7 GB RAM.
- Skinned SH2 characters (James, Maria, etc.) are not covered by the FPV LOGIC UE5 note, which handles StaticMesh only. The BTD6 note warns that skinned meshes are stored in bind/T-pose and need clip evaluation.
- The toolkit says to stay 'playable with placeholders when the pack is missing', while Melty forbids look-alike stand-ins and requires an in-game message. Neutral placeholders plus a clear missing-game message must be reconciled with Melty's rule.
- Mislabelling the route as 'geometry transfer' or 'passthrough' would import techniques for running guests (render-state restore, streaming budgets) that do not apply. The toolkit explicitly warns about route-vocabulary mix-ups.
- Guest updates change bundle hashes and typetrees (BTD6), so a cache that is not keyed to each guest's build silently goes stale.
- Testing cannot happen from this Linux cloud container (um win refuses on Linux, and no games are installed). Anything verified here is at best a synthetic test, not a real run.
- Licenses of third-party readers the converter might bundle (UnityPy, CUE4Parse/FModel, Oodle DLL) were not checked in this track. The FPV note loaded Oodle from another installed game's DLL, which a Melty bundle cannot assume.

## Katamari real RULES as design-sheet data (pickup, growth, stage structure, controls, Once Upon A KATAMARI specifics, object tiers) + minimal faithful ruleset for a first playable stage

The best source turned out to be a community datamine of Katamari Damacy REROLL, not the wikis. The wikis (fandom, Katamaripedia, StrategyWiki, GameFAQs, speedrun.com, Steam) are all blocked by this sandbox's egress proxy, so those facts come only from search-engine snippets and are marked 'likely'. github.com, raw.githubusercontent.com and Google Docs/Sheets exports were reachable. Through them I read two things: the REROLL speedrun notes (shookietea/reroll-notes) and the two documents they link. One is a 1718-row data dump of REROLL objects and missions (each object's volume, required pickup size and growth factor, plus each mission's start/goal/time/rating table). The other is a 'Size Growth Document'. The exact pickup rule is now confirmed against the data. An object can be rolled up when the katamari, treated as a sphere, has at least 10x the object's volume. Each object's required size is that diameter rounded down to the millimetre, and this formula matched 1466 of 1467 objects. Equivalently, the object's sphere-equivalent diameter must be 46.4% of the katamari diameter or less. Growth adds the object's volume times a per-object factor (0.8 for most objects), and that amount drops off once the katamari passes the stage goal. The displayed size is the diameter of the katamari's total volume treated as a sphere. The prompt's 'Make a Star 1 = 10 cm to 1 m in 4 min' is wrong. In REROLL, MAS1 is 5 cm to a 10 cm goal in 4 minutes, with rating sizes of 10/12/14/15 cm (the PS2 original reportedly gave 3 minutes). The 1 m goal belongs to MAS4 (5 cm to 1 m in 10 minutes). Dash ('Charge'n'Roll') timings are frame-documented: game logic runs at 30 fps, alternating stick inputs must come within 0.4 s, a spin starts at 3 inputs, and a boost at 5 (when under 50 cm). Once Upon A KATAMARI (OUAK) has nine eras, a one-button dash option, a 'simple' control scheme, and four 10-second power-ups (Magnet, Rocket, Timer, Sonar/Radar), with only one held at a time. Each stage has 3 crowns, plus cousins and presents to collect, and D-to-S ranks. Its first real stage reportedly asks for 15 cm in 4 minutes. OUAK is a Unity IL2CPP/URP game modded with MelonLoader (namespace Il2CppApp.KatamariSin). OUAK's own per-object pickup and growth numbers are NOT public, so the REROLL formulas are the best sourced stand-in. The mod should derive object volumes from the OUAK meshes it loads, and that conversion is a tuning step.

**Risks**
- Every hard number (pickup rule, growth factors, MAS1 table, dash frames) comes from Katamari Damacy REROLL, not Once Upon A KATAMARI. OUAK may use different constants, and one unreadable Steam thread hints its growth may be additive. The mod must call its rules 'REROLL-faithful' unless OUAK data is extracted.
- The objects the mod loads come from the player's OUAK install, and their volumes and pickup sizes in OUAK are unknown. Volumes estimated from mesh bounding boxes will be too large for hollow or thin objects (umbrellas, shelves), and REROLL uses per-object authored volumes. A volume fill factor per object or category has to be tuned in the real game.
- The datamine and growth document are community work hosted on Google Docs. They could change or disappear, so the design sheet should copy the numbers it uses with a citation and the date retrieved (2026-10-08).
- The growth-decay curve is measured, not decompiled, and splitting it into per-object factor x stage multiplier is my inference. The METEOR column's meaning (time limit in minutes for a comet) and MAX_DIAMETER (a hard cap?) are inferred.
- The knock-off rule (how many objects fall off, at what impact speed) has no sourced numbers, so it is pure tuning.
- Most wiki/guide facts come from search-engine snippets: fandom, Katamaripedia, StrategyWiki, GameFAQs, speedrun.com, Steam, Wikipedia, Neoseeker and PowerPyx were all blocked by the sandbox proxy, so the pages could not be read in full. Reviewers disagree on OUAK's simple-control layout and on cousin totals.
- Reimplementing rules and numbers is fine, but the release must not ship REROLL's object list or names as content. Real content must come only from the player's own OUAK/SH2 installs, per Melty rules.
- The 30 Hz frame timings must be converted to seconds for the host's tick rate, or dash feel will differ.

**Recommendation**

Base Stage 1 on Katamari Damacy REROLL 'Make a Star 1', the only stage with complete datamined numbers, and play it as James in an SH2-styled room. Every rule cites a source; values marked TUNE are placeholders to check in the real game. Data-sheet shape:
1) STAGE. start_diameter = 5.0 cm (+0.02 cm display offset); goal = 10 cm; time_limit = 240 s; rating_bands = [10, 12, 14, 15] cm; size_cap = 30 cm. Source: REROLL missions sheet gid 2077912482; the cap's meaning is a guess. Optional comet ('fast clear') if the goal is reached within 60 s (METEOR = 1; meaning likely). The timer starts on first movement or pickup (OUAK MainGameManager.PlayTime behaviour).
2) SIZE. diameter_cm = 100*(6*V/pi)^(1/3) + 0.02, where V is the katamari volume in m^3 (growth document).
3) PICKUP. Allowed iff diameter_cm >= pickup_cm, where pickup_cm = floor_mm(100*(60*V_obj/pi)^(1/3)). In words: the katamari needs 10x the object's volume, or object sphere-equivalent diameter <= 0.464 x katamari diameter. Verified on 1466/1467 REROLL objects. V_obj for an OUAK mesh = AABB volume x fill factor (TUNE, start about 0.35 and check against REROLL anchors: caramel 4.4 cm, pushpin 3.5 cm, mandarin 14.1 cm). If OUAK's own size data can be read, use it instead.
4) GROWTH. On pickup, V += V_obj * f_obj * m(D). f_obj defaults to 0.8 (0.4 for tiny bugs, 0.5 for drinks/books, 0.26 for doors; object db). m(D) = 1.0 up to 10 cm, falling linearly to 0.5 at 15 cm and 0.2 at 20 cm, then held at 0.2 (MAS1 curve / 0.8; the split into two factors is inferred). Stock the room with about 2x the volume the goal needs: the goal needs 4.58e-4 m^3 added, and the MAS1 map alone supports about 20.9 cm.
5) OBJECT TIERS. 20-40 kinds, 250-350 placements (TUNE), in 5 tiers taken from the REROLL MAS1 pickup sizes:
- T1, 1.5-4.5 cm, 'The Smallest': ants, matches, buttons, dice, screws, pushpins, coins, caramels. About 40% of placements, in many copies.
- T2, 5.1-7.6 cm: soy sauce pack, cookies, candy, mandarin piece, matchbox, eyedrops, eraser, lipstick.
- T3, 8.0-9.8 cm: cherries, cheese, film, battery.
- T4, 10.3-14.2 cm: phone, mouse, tape, nail clipper, mandarin. These are the post-goal rating bait.
- T5, 17-25 cm: watermelon slice, eggplant, teacup, rice bowls. Reachable only for the top rating.
Unpickable 'walls' of 35 cm and up (teddy 34.8, TV 86.7, sliding doors 154-159). Fill each tier with REAL OUAK objects of similar real-world size, and use SH2 objects only as set dressing and audio, as the concept allows. Optional size gate: a REROLL-style 'Over 10cm' blocker (add factor 0.01) before a second area.
6) MOVES.
- Tank twin-stick: both forward = roll; opposite = rotate in place.
- One-stick 'simple' scheme (OUAK).
- Dash: one-button instant dash (OUAK style) PLUS classic alternating input. Inputs must alternate within 0.4 s; spin at 3; boost at 5 under 50 cm; energy 8 s of spin/boost; +0.6 s recharged per 3.33 s idle; 8 s 'huff' lockout at 0 (reroll-notes boosts.md, frames / 30).

- Small steps are climbable; pushing into a wall climbs it (TUNE height ~0.5 x D).
- No jump or power-ups in stage 1. OUAK freebies (Magnet, Rocket, Timer, Sonar at 10 s each, one held) can come later.
7) COLLISIONS. Hitting an unpickable object or wall above a speed threshold (TUNE) detaches the most recent 1-3 objects (TUNE; no sourced numbers) and resets the dash count (sourced). Moving NPCs must be struck first unless D >= TUNE x their pickup size; animals can be rolled up as-is (REROLL tutorial text).

- Katamari namespace. Track 1 says App.KatamariSin (BepInEx 6 Il2CppInterop, from ItsSeafoamy Plugin.cs). Track 5 says Il2CppApp.KatamariSin (MelonLoader-generated assemblies). Both are right: the 'Il2Cpp' prefix depends on the interop generator. It only matters if we read MonoBehaviour data through Cpp2IL type layouts.
- Cousin count. Track 1 says Prince plus 68 cousins (69 royals). Track 5's guides give 68 or 69 cousins. The figures fit if 69 counts the Prince. Minor, and irrelevant because SH2 characters replace them.
- Toolkit vs Melty on missing content. The toolkit's Pattern 5 says 'stay playable with placeholders when the pack is missing' (.../skills/mashup-mods/SKILL.md). Melty forbids look-alike stand-ins and requires an in-game message. Resolution: neutral greybox shapes that imitate neither game, plus a blocking message that names the missing game and its Steam id. Placeholders must never imitate Katamari props or SH2 characters.
- Stage-1 numbers. Track 5 recommends Katamari Damacy REROLL Make a Star 1 (5 to 10 cm in 240 s, fully datamined). It also reports Once Upon A KATAMARI's 'As Large As Possible 1' as 15 cm in 4 min (Neoseeker snippet). These are not contradictory facts, but the design sheet has to label the rules 'REROLL-derived', because no OUAK constants are public.
- Katamari save path. Track 1 reports %LOCALAPPDATA%\BANDAI NAMCO Entertainment\Once Upon A KATAMARI\Saved\SaveGames, from a PCGamingWiki search summary. 'Saved\SaveGames' is Unreal's layout, which is odd for a Unity IL2CPP game. My recheck search found no source. Treat it as unverified. It does not affect the design, because the mod never touches Katamari saves.
